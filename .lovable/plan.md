## What's happening

`.env` in this project is regenerated by the Lovable/Supabase connection and currently only contains:

```
VITE_SUPABASE_PROJECT_ID
VITE_SUPABASE_PUBLISHABLE_KEY
VITE_SUPABASE_URL
```

`VITE_DEMO_EMAIL`, `VITE_DEMO_PASSWORD` and `VITE_CREATOR_EMAIL` were added earlier but are no longer there — the file got rewritten. Since `src/lib/demo-user.ts` reads `import.meta.env.VITE_DEMO_EMAIL || ''` and `Auth.tsx` prefills from those values, they resolve to empty strings, so the sign-in form shows blank fields and demo read-only detection silently fails.

The email is still literally in code in 4 places, all as fallbacks added at different times:
- `supabase/functions/mcp/index.ts:32`
- `supabase/functions/encrypt-existing/index.ts:9`
- `supabase/functions/financial-api/index.ts:133`
- `src/lib/mcp/lib/supabase.ts:28`

## Plan

**1. Frontend config that survives .env rewrites**

Create `src/config/app-config.ts` as the single source for demo/creator identity:

```ts
export const DEMO_EMAIL = (import.meta.env.VITE_DEMO_EMAIL ?? 'user@yopmail.com').toLowerCase();
export const DEMO_PASSWORD = import.meta.env.VITE_DEMO_PASSWORD ?? 'userAssets@123';
export const CREATOR_EMAIL = (import.meta.env.VITE_CREATOR_EMAIL ?? 'ashdeveloper8@gmail.com').toLowerCase();
```

Env vars win when present; the fallback keeps the demo working when `.env` is regenerated. These are intentionally public values (a shared demo login + an identifier), not secrets — RLS and the server-side `demo_editable` check are what actually protect data.

Then `src/lib/demo-user.ts` and `src/pages/Auth.tsx` import from this module instead of reading `import.meta.env` directly, restoring the prefilled sign-in credentials and the masked-password behaviour.

**2. Restore the env entries**

Re-add `VITE_DEMO_EMAIL`, `VITE_DEMO_PASSWORD`, `VITE_CREATOR_EMAIL` to `.env` (and keep them documented in `.env.example`) so a deployment can override the defaults.

**3. Deduplicate the backend copies**

Add a shared `supabase/functions/_shared/config.ts` exporting `DEMO_EMAIL` / `CREATOR_EMAIL` read from `Deno.env` with the same fallback, and have `financial-api`, `encrypt-existing`, `mcp`, and `src/lib/mcp/lib/supabase.ts` import it — so the string exists once per runtime instead of four times.

**4. Verify**

Load `/auth?mode=signin` in a headless browser and confirm the email field shows the demo address, the password is prefilled and masked with no reveal toggle, and switching to Sign up clears both fields.

If you'd rather the demo email never appear in the repo at all, the alternative is to drop the fallbacks and accept that the prefill breaks whenever `.env` is regenerated — say the word and I'll do that instead.
